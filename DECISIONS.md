# KipuVault — Registro de Decisiones de Ingeniería

| ID | Decisión | Justificación / Seguridad |
| --- | --- | --- |
| D-01 | **Anchor `0.30.1` + `anchor-bankrun 0.5.0` + `solana-bankrun 0.4.0` + `@solana/web3.js 1.98.4`** | `anchor-bankrun@0.5.0` declara peerDependencies `@coral-xyz/anchor@^0.30.0`, `solana-bankrun@>=0.2.0 <0.5.0` y `@solana/web3.js@>1.92.0`. Fijar `0.30.1` y `1.98.4` evita incompatibilidades de ABI y breaking changes de `@solana/web3.js` v2/v3. |
| D-02 | **Validaciones de `agent_execute` en orden secuencial dentro del handler** | Anchor valida atributos de `#[derive(Accounts)]` antes del cuerpo de la instrucción. Para garantizar el orden determinista 1→11 exigido en `SPEC.md` §4.3 (por ejemplo `UnauthorizedAgent` antes de `VaultFrozen` antes de `InvalidAmount` antes de `InvalidDecisionHash` antes de `InvalidMint` antes de `RecipientNotAllowed`), las comprobaciones 1–9 se ejecutan explícitamente en orden dentro de `agent_execute`. |
| D-03 | **`add_recipient(Pubkey::default())` retorna `KipuError::InvalidPolicyConfig` (6005)** | `SPEC.md` §4.4 define exactamente los códigos 6000–6013 y no incluye un código `InvalidRecipient`. Rechazar `Pubkey::default()` con `InvalidPolicyConfig` comunica con precisión que la configuración de la política/allowlist es inválida sin alterar la numeración 6000–6013. |
| D-04 | **`update_policy` y `initialize_vault` también rechazan `agent == Pubkey::default()`** | Además de `agent != owner`, rechazar la clave cero evita dejar una bóveda sin agente válido o manipulable accidentalmente, devolviendo `InvalidPolicyConfig`. |
| D-05 | **Keypairs de Devnet generadas en `keypairs/` (gitignored)** | Ninguna clave privada se almacena en código o archivos versionados. `scripts/setup_devnet_usdc.ts` guarda keypairs locales en `keypairs/` (ignorado en `.gitignore`) y publica solo direcciones públicas en `scripts/devnet-output.json`. |
| D-06 | **Program ID inicial sincronizable con `anchor keys sync`** | Mientras el usuario compila el binario `.so` en GitHub Codespaces, se declara un Program ID base58 válido provisional en `lib.rs` y `Anchor.toml`; al ejecutar `anchor build && anchor keys sync` se alinea con `target/deploy/kipu_vault-keypair.json`. |
| D-07 | **Mirror inicial de `kipu_vault.json` en `frontend/src/idl/` + `npm run sync:idl`** | Permite compilar y validar Next.js (`npm run lint && npm run build`) antes de generar `target/idl/kipu_vault.json` en Codespaces; tras `anchor build`, `npm run sync:idl` sobrescribe `frontend/src/idl/kipu_vault.json` con el IDL emitido por Anchor. |
| D-08 | **Handlers con nombre único en `programs/kipu_vault/src/instructions/`** | Evita colisiones de `ambiguous_glob_reexports` al re-exportar cuentas desde `instructions/mod.rs` en Rust `1.79.0`. |
| D-09 | **Sustituido: Rust `1.79.0` + Anchor `0.30.1` reemplazada por stack vigente (ver D-11)** | Histórico: el toolchain heredado de 2024 chocó en CI con crates de 2026 (`edition2024`, MSRV > 1.75 en `platform-tools` y `proc-macro2::Span::source_file`). Se migró el stack completo a Rust `1.89.0` + Agave `4.1.2` + Anchor `1.2.1`. |
| D-10 | **Sustituido: pines transitivos en `[dev-dependencies]` eliminados en Anchor `1.2.1`** | Al actualizar a Rust `1.89.0` y Anchor `1.2.1`, se retiraron todos los pines temporales de `[dev-dependencies]` en `programs/kipu_vault/Cargo.toml`. |
| D-11 | **Stack objetivo Rust `1.89.0` + Agave `4.1.2` + Anchor `1.2.1` (`solana-v4`)** | `anchor-lang = 1.2.1` y `anchor-spl = 1.2.1` habilitan la feature `solana-v4` con `default-features = false` (evitando conflicto con `solana-v3`), manteniendo Rust `1.89.0`, sin dependencia directa de `solana-program` y con tipos base importados desde `anchor_lang::prelude::*`. |
| D-12 | **Sintaxis `CpiContext` de Anchor 1.x en `deposit`, `withdraw` y `agent_execute`** | En Anchor `1.x`, `CpiContext::new` y `CpiContext::new_with_signer` reciben `program_id: Pubkey` (`ctx.accounts.token_program.key()`) en lugar de `AccountInfo` (`to_account_info()`). Se actualizaron las tres invocaciones SPL Token (`TransferChecked`). |
| D-13 | **Cliente `@anchor-lang/core@1.2.1` en reemplazo de `@coral-xyz/anchor`** | Se eliminó `@coral-xyz/anchor` de `package.json` y `frontend/package.json` y se actualizaron todos los imports en `tests/`, `scripts/` y `frontend/src/lib/kipuVault.ts` al paquete vigente `@anchor-lang/core@1.2.1` bajo Node.js `22` LTS (`>= 20.18`). |
| D-14 | **Tests con `anchor-litesvm@0.2.1` + `litesvm@1.6.2` y adaptador Web3 (`tests/litesvm_compat.ts`)** | `litesvm@0.3.3` presentaba el fallo `LiteSVM/litesvm#171` (`std::bad_alloc` en `linux-x64` por estado x87 FPU tras ejecutar transacciones), corregido en upstream PR `#398` (`litesvm >= 1.4.0`). Se fijó `litesvm@1.6.2` manteniendo `LiteSVMProvider` de `anchor-litesvm@0.2.1` mediante `tests/litesvm_compat.ts` (que envuelve `litesvm/dist/internal` `LiteSvm` para `@solana/web3.js` v1, acota `rentEpoch` de Agave 4 `u64::MAX`, fija un `unixTimestamp` inicial no nulo y avanza exactamente `86_400n` s con `svm.getClock()` / `svm.setClock(clock)`). |
| D-15 | **Instalación explícita de `cargo-build-sbf` y binario oficial de Anchor `1.2.1` + `--skip-deploy` en CI** | Compilar `anchor-cli@1.2.1` desde crates.io exige `rustc 1.91` por `cargo-platform@0.3.3`; mantener Rust exacto en `1.89.0` requiere usar el binario precompilado oficial `anchor-1.2.1-x86_64-unknown-linux-gnu` de GitHub Releases. Además, CI/`.devcontainer/setup.sh` verifican `cargo-build-sbf` y usan `anchor test --skip-local-validator --skip-deploy --skip-build` para evitar pre-despliegues RPC al ejecutar LiteSVM en memoria (en validator externo se usaría `--validator legacy` solo si Surfpool fallara). |
| D-16 | **Runner Mocha + `ts-node/register` con `--no-experimental-strip-types` en Node `22+`** | Node `22.18+` habilita `--experimental-strip-types` por defecto, haciendo que Mocha cargue archivos `.ts` vía ESM nativo en lugar de `ts-node` CommonJS (y falle con `Named export 'BN' not found` contra `@anchor-lang/core` CommonJS). Invocar `node --no-experimental-strip-types ./node_modules/mocha/bin/mocha.js --require ts-node/register` en lugar de `ts-mocha` (que re-lanza subprocesos sin conservar flags de Node) garantiza ejecución CommonJS determinista. |
| D-17 | **Runner CI y Devcontainer sobre Ubuntu `24.04` (glibc `2.39`)** | El binario nativo NAPI `litesvm-linux-x64-gnu@0.3.3` requiere `__isoc23_strtol` (glibc `>= 2.38`) y el binario oficial precompilado de Anchor `1.2.1` apunta a `GLIBC_2.39`. Usar `ubuntu-24.04` en `.github/workflows/ci.yml` y `.devcontainer/devcontainer.json` evita `ERR_DLOPEN_FAILED` sobre Ubuntu `22.04` (glibc `2.35`). |
| D-18 | **Compilación nativa SBPF v3 con `litesvm@1.6.2` (sin fallback `--arch v0`)** | `litesvm@1.6.2` (basado en Agave `4.x`) soporta de forma nativa los binarios SBPF por defecto de Agave `4.1.2` + Anchor `1.2.1`, por lo que `anchor build` corre sin forzar `--arch v0` ni `ANCHOR_BUILD_SBF_ARCH`. |
| D-19 | **Soporte para Meta Model API (`LLM_PROVIDER=meta`)** | Se añadió `MetaLLMClient` en `backend/app/services/llm.py` usando `httpx` sobre `META_API_BASE_URL/chat/completions` (por defecto `https://api.meta.ai/v1`) con salida estructurada estricta (`response_format.type = "json_schema"`, todos los campos requeridos y `additionalProperties: false`) a `temperature=0`, sin agregar dependencias nuevas. |
